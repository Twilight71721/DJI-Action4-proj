# 给 Windows Codex 的 Action 4 v6 视频引导数据集 Prompt

把下面整段内容复制给 Windows 电脑上的 Codex。视频路径为C:\exam-project\vedio。工作仓库预计为
`C:\exam-project\Blender-repo`。

```text
你现在负责改进 DJI Action 4 的 Blender/BOP 合成数据，使它更接近真实头戴相机视频。
你没有此前对话记忆。请把本任务当作一次“真实视频引导的合成域修正”，先检查证据，
再修改代码；不要直接批量生成正式训练集。

仓库：
C:\exam-project\Blender-repo

真实参考视频：
C:\exam-project\vedio

重要背景：

1. 下游网络是 instance-level BB8：输入单个 DJI Action 4 的 bbox crop，输出 8 个
   三维包围盒角点的二维热图。渲染结果必须保持完整 BOP 标签、mask、mask_visib、
   scene_camera.json、scene_gt.json、scene_gt_info.json 和八角点投影一致。
2. 当前 v4 GLB 几何、坐标对齐、统一缩放和角点顺序已经通过验证。不要重新定义角点，
   不要用 PLY 替换 GLB，不要破坏 UV/PBR 纹理，不要对三个轴分别缩放。
3. 训练阶段不要求标定真实视频相机。为了提高跨相机泛化，应在合成数据中随机化合理的
   焦距/FOV、主点小扰动、相机距离和构图。不要把某一台真实相机的 K 固定为唯一训练 K。
4. 但是不要声称“无需 K 就能得到精确 PnP 位姿”。当前任务只负责训练数据和二维角点；
   将来进行度量 6D pose/PnP 时仍需运行时 K、合理近似 K，或另行实现未知焦距求解。
5. 真实视频里的 Action 4 后屏是亮屏，会显示实时画面和 UI，不是纯黑屏。视频中还可见
   黑色机身、腕带/底座、线缆、手臂、白色编号标签和 AprilTag。必须把这些差异纳入审计。

一、先做只读检查，不要立即修改或渲染 5000 张

- 进入仓库，完整阅读 AGENTS.md（如果存在）、README、WINDOWS_HANDOFF.md、现有渲染、
  资产准备、BOP 写入、角点投影和验证脚本。
- 运行 `git status --short`，记录现有未提交改动；不得覆盖 v3/v4/v5 或固定八视角目录。
- 验证真实视频路径存在，使用 OpenCV/ffprobe 报告分辨率、帧数、FPS、时长和编码。
- 从整段视频按时间均匀抽取至少 24 帧，另外在开头、中间、结尾各密集抽取若干帧；输出
  contact sheet。不要只看一帧，不要只看正面。
- 从抽帧中分别收集左、右两台相机的代表性 ROI（仅用于分析），覆盖正面、背面、侧面、
  斜角、靠近画面边缘、部分遮挡和运动状态。保存审计图，但不要把真实帧直接复制、贴图
  或合成进训练 RGB。
- 基于可见证据写 `real-video-domain-audit.md`，至少分析：
  - 机身颜色、屏幕开关与亮度、镜头环高光；
  - 亮屏内容、UI、AprilTag、顶部白色编号标签；
  - 底座、腕带、绿色包边、线缆、手和手臂；
  - 背景颜色与结构；
  - 遮挡、截断、物体尺寸、清晰度、曝光、白平衡和运动模糊；
  - 左右相机是否存在系统性外观差异。
- 对无法从视频可靠测量的量明确写“未知”，不要伪造精确统计。若没有检测器/人工 bbox，
  可以报告代表性 ROI 和目测范围，但不得声称是全视频真实分布。

二、先修正最明显的外观域差异

请优先检查材质，而不是通过整体压暗画面掩盖问题：

- 机身主体应为接近真实视频的黑色/深灰色，并保留塑料的粗糙度和边缘细节。
- 镜头环保留受控金属高光，不允许大片过曝、镜面银白或反射出不存在的环境图案。
- 后屏必须有“关闭”和“亮屏”两种状态；分布以真实视频审计为依据。由于参考视频中屏幕
  明显为亮屏，pilot 中亮屏应占多数。
- 亮屏不能是一块均匀白色或均匀蓝色。请使用程序生成或仓库合法资产构造低风险的动态
  屏幕内容，例如灰墙、肤色/手臂、白色台面、取景画面、状态栏、电量和录制 UI。不要
  直接截取真实视频帧作为屏幕纹理，以免把评估数据泄漏进训练集。
- 屏幕应使用受控 emission，与环境曝光解耦但不过曝；随机化亮度、色温和 UI 状态。
  必须保留可见边框和屏幕内细节，不能让整块屏幕饱和成白色。
- 若用额外平面实现屏幕/贴纸，必须解决 z-fighting，并保证它随物体刚性运动。属于相机
  本体的屏幕/贴纸应在 RGB 与对象 mask 中一致；腕带、底座、线缆、手臂等附件不能被
  错写进 Action 4 的对象 mask。
- 加入顶部白色编号标签和后屏 AprilTag 的可控变体，但不要让标签成为每张图唯一不变的
  捷径。位置、是否出现和轻微磨损可随机化，角点标签仍对应相机本体的固定三维包围盒。

三、加入真实域结构，但保持标签语义正确

- 优先复用仓库已有且来源合法的三维资产。若没有可靠的真实手模型，不要声称简单几何体
  是“真实手”；可把它标为近似前景遮挡物。
- 至少加入：黑色安装底座、灰黑腕带/表带、绿色边缘细节、弯曲黑色线缆、肤色手臂或
  合法手部资产，以及与视频类似的灰墙、白色带网格台面/区域、深色衣物等背景类型。
- 固定附件（底座、腕带、线缆起点）应与 Action 4 保持合理相对关系，再整体随机姿态；
  不能每帧漂浮到不可能的位置。
- 遮挡物必须真实遮挡 RGB、depth 和 mask_visib，但不能进入完整对象 mask。必须用像素
  计算 `visible_pixels / full_mask_pixels`，不允许用场景参数估算可见比例。
- 初始目标遮挡分布：55% 为 0--5%，30% 为 5--20%，15% 为 20--35%；拒绝可见比例
  小于 60% 的样本。根据真实视频审计可以小幅调整，但要在报告中说明依据。
- 通用白色/灰色方块最多占 10%，不能成为主要遮挡来源。
- 加入轻度边缘截断：建议约 70% 完整入画、20% 轻微截断、10% 明显但仍可识别。截断后
  仍保存真实投影角点；不得把越界角点 clamp 到图像边界，也不得移动角点去贴可见轮廓。

四、相机泛化和图像质量

- 不要求对参考视频相机做棋盘格/ChArUco 标定，也不要把标定作为本轮阻塞项。
- 在保持 640x480 合成输出和 BOP 一致性的前提下，随机化 pinhole 相机焦距/FOV、主点小
  扰动、方位角、俯仰角、roll、距离和非中心构图。参数范围必须记录到 metadata。
- 不要为了“模拟广角”只扭曲 RGB。任何可选畸变增强都必须同步变换 RGB、mask、
  mask_visib、depth 和二维角点，并保存畸变参数；否则先不加入畸变。
- 下游会按 bbox 从原图裁剪并 resize 到 256x256，因此重点保证对象 crop 的纹理可读。
  检查 GLB 的 4096 纹理是否实际连接到 Base Color/Normal/Metallic-Roughness，检查屏幕和
  机身在对象宽度约 128--300 像素时是否仍有细节。
- RGB 使用无损 PNG；不做二次 JPEG。可加入小比例、轻量的曝光/白平衡/传感器噪声和
  运动模糊，但不能让标签语义含糊，也不能用强模糊掩盖材质问题。
- 对 Cycles samples、denoising、纹理插值做固定姿态 A/B。选择能保留镜头环、按钮、文字
  和亮屏 UI 细节的设置；报告渲染耗时与显存。不要凭主观印象声称“高清”。

五、先做固定姿态 A/B，再生成 200 张 pilot

1. 使用同一组正面、背面、左右侧、四个斜角姿态，分别渲染修改前/修改后结果。相机 K、
   R、t、随机种子和构图必须相同，以便只比较材质、亮屏和附件。
2. 输出 A/B contact sheet，以及亮屏、镜头环、机身、标签和 mask 边界的局部 crop。
3. 确认没有 z-fighting、整屏过曝、mask 漏屏幕、附件混入对象 mask、角点错位后，才生成：

   dataset\action4-v6-domain-pilot-200

4. pilot 至少包含 5 个 scene、固定随机种子、完整 BOP 输出和角点投影记录。不要覆盖任何
   旧目录；目录已存在时停止并换一个明确的新名字。
5. 运行现有全部验证器，并新增/扩展验证以检查：
   - K/R/t 与投影代码实际使用值一致；
   - 8 个角点编号固定、深度为正，允许按设计越界但不得被 clamp；
   - RGB/depth/mask/mask_visib 尺寸一致，mask_visib 是 mask 子集；
   - 屏幕/贴纸属于本体时对象 mask 连续，附件不进入对象 mask；
   - 遮挡比例严格来自 mask 像素；
   - 无 NaN/Inf、空 mask、全零 depth、饱和屏幕或大面积过曝；
   - 亮屏/关屏、附件类型、背景、截断、姿态和对象 crop 尺寸均有分布统计。

六、交付物和停止条件

- 输出 `validation-summary.json`、`validation-report.md`、参数/随机种子、性能报告、至少
  32 张均匀覆盖失败风险的 overlay，以及原始 RGB contact sheet。
- 从 200 张中用确定性规则选 32 张生成 regression 包，保留原始 frame id 和相对路径。
  regression zip 不要包含约 92 MB 的 GLB、缓存、环境、旧数据集或绝对 Windows 路径。
- 报告所有修改文件、运行命令、实际检查结果和仍未解决的风险。
- 不要生成 5000/10000 张正式训练集，不要 commit，不要 push。完成 200 张 pilot 和报告后
  停止，等待我与 Linux 训练仓库做兼容性检查。

判定标准：标签正确只是最低要求。只有当 RGB 外观明显接近真实视频中的黑色 Action 4、
多数样本具有受控亮屏、附件/遮挡关系合理、crop 细节清晰，而且验证仍全部通过时，pilot
才算成功。若 GLB 材质或屏幕几何无法可靠修改，请明确指出具体资产/节点/材质限制并停止，
不要用整体调暗、后期涂块或伪造验证结果绕过问题。
```

## 使用边界

这份 prompt 把真实视频作为**开发参考域**，不要求先标定相机，也不会把视频帧复制进
训练数据。因为它已被用于参数设计和质检，这段视频之后更适合作为开发验证集；最终性能
报告最好再保留一段没有参与设计的新视频。
